01

System map — one event's whole journey

Two money boundaries define the architecture. Above the first, every microsecond is billed to the customer. Below the second, every byte is billed to us. In v1 the agent is required, not optional — it sits on their machine but in our process, which is precisely why it is the cheapest place to do expensive work.

02

Inside the host — the line between 5µs and everything else

The hot path runs on every request and does four things, none of which touch the OS. Everything expensive — stack parsing, redaction, fingerprinting, compression — happens on the other side of the ring buffer, where being slow is free.

03

The fold — where four orders of magnitude go

One bad deploy, ten seconds, forty pods, fifty thousand throws. An event-oriented SDK transmits all of it. Grouping by fingerprint before the network turns 250 MB into roughly 41 KB while keeping exact counts, accurate percentiles, and full stacks.

The cost we accept

Fingerprinting client-side makes the algorithm part of the wire contract, so version skew across customer SDK deployments is real. Two mitigations carry it: raw grouping inputs travel alongside the hash so the server can re-fingerprint on demand, and the durable log stays replayable so history can be recomputed when the algorithm improves.

04

Direct mode versus agent mode — what actually moves

Same system, two wirings. Mode B is the required v1 path for every backend-hosted SDK; Mode A survives only as the fallback for environments with no host process to run an Agent on. The argument was never that the agent is faster — it's that five entire categories of failure leave the customer's process. Compare the height of the amber box on each side.

05

Backpressure — a closed loop and a state machine

Two independent mechanisms. The loop protects us from customers; the state machine protects customers from us. Neither works without the other, and the second is how a monitoring agent avoids becoming the outage it was bought to detect.

06

Ingest edge — six stages, none of which read the payload

The front door does the least work of any component in the system. It validates an envelope header, checks a quota, reads one priority byte, appends opaque bytes, and returns 202. Parsing untrusted input is both the latency floor and the security surface, so it happens later, where a crash is a retry.

07

Sampling — where the decision is made, and what it costs to wait

The same request, drawn three times. The only variable is when the keep or drop decision happens, and every consequence in the design follows from that one choice of moment.

08

Storage fan-out — the v2 growth path, once the log is triggered

Not what v1 runs — v1 is plate 01's single write straight into the org's MongoDB database, no queue. This is what gets added if one of §10's growth triggers fires: write contention, a fingerprint-algorithm change needing full replay, or a second independent consumer. The replay arrow is the reason a log would earn its cost: when the fingerprinting algorithm improves, history is recomputed rather than abandoned.

Why the fold is architecture, not optimization

The gap between 2.2 GB and 15 MB per customer per day is the gap between a business and an S3 bill with a dashboard attached. A fold added later cannot reach it, because the wire format, the storage schema and the query layer would all have been built around events.

Two rows in that table are qualitatively different from the rest. Fork-safety and internal SDK errors are the only failures that damage the host rather than merely losing our own data — and both are silent. Everything else degrades into a counted drop, which the meta record surfaces honestly. These two are the reason the invariant list is a test suite and not a memo.

Decisions — resolved

Actual scale at time of writing
2–3 organizations, all pre-production, ~4 SDK installations total. That number is why each resolution below reads the way it does.

#DecisionResolutionReasoning
01SaaS or self-hosted firstmulti-tenant, day oneMongoDB, one database per org (plate 01). Real orgs exist today, so isolation can't be deferred the way quota/billing can — and at 2–3 orgs, database-per-org is structural isolation for free, not a cost.
02First SDK languageNodeWorker threads move serialization, compression and fingerprinting off the event loop without fighting the GIL or fork-safety — the cleanest environment to prove the fold logic in first.
03Agent in v1 or v2v1 — requiredReopened from the original default. Every backend-hosted SDK talks to a host-local Agent over UDS (plate 04); direct/HTTPS survives only as the browser/mobile/serverless fallback.
04Scale target for v1schema big, infra smallDatabase-per-org isolation and the fold's field shape are built for growth now. Kafka, HLL/DDSketch, and quota enforcement are deferred — see growth triggers below — because infra topology is cheap to change later and schema is not.

Growth triggers — what brings each deferred piece back

Each trigger is a measurement, not a date. Building ahead of the trigger was considered and rejected for each of these — a single-broker Kafka gives no real durability gain over MongoDB directly, and HLL/DDSketch are measurably less accurate than exact counts at pilot volume.

Everything drawn is a target, not a measurement. The first real work is the benchmark harness from plate 02 — until the hot path is measured under load in a host application, “< 5 µs” is an intention. The second is the fold table from plate 03, because its cardinality behaviour under a storm decides whether the ratio in the volume table survives contact with production.
